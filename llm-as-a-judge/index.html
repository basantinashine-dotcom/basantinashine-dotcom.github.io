LLM-as-a-Judge

Pitfalls, biases and production fixes

An LLM judge is a model that grades another model’s output against a rubric. It’s the only way to check subjective quality at scale, and it’s easy to get wrong: judges have predictable biases, and their scores drift. This guide covers the biases, the fixes, and how to prove a judge is reliable before you trust it.

When to use

Between code checks and people

Use code assertions for anything you can check exactly: format, length, the right tool call, the final state. Use people for ground truth and hard cases. An LLM judge fills the gap: subjective quality, like tone or helpfulness, checked on every output, in seconds, for a fraction of what reviewers cost.

The trade: it’s cheaper and faster than people, but less consistent than code and less accurate than experts, so it has to be checked against them.

The four major judge biases

What skews a judge, and the fix for each

Bias 1 · Position

The first answer wins too often

In pairwise comparisons, judges favor whichever answer they see first (or, for some models, last), whatever it says.

Fix: run every pair in both orders. Count a win only if it survives the swap; if the verdict flips, call it a tie.

Sources: Zheng et al., Judging LLM-as-a-Judge ↗ · Wang et al., LLMs are not Fair Evaluators ↗

Bias 2 · Verbosity

Longer looks better

Judges tend to rate longer answers higher, even when the extra words add nothing. Length gets mistaken for quality.

Fix: say in the rubric that length isn’t quality and that padding counts against an answer. Compare answers of similar length, or adjust for length when you report win rates.

Sources: Zheng et al. ↗ · Dubois et al., Length-Controlled AlpacaEval ↗

Bias 3 · Self-enhancement

Judges prefer their own writing

A judge tends to favor outputs that sound like it, so when the same model, or model family, both writes and grades, scores come out inflated.

Fix: use a judge from a different model family than the generator, or a small jury of diverse models and take the majority.

Sources: Panickssery et al., LLM Evaluators Favor Their Own Generations ↗ · Verga et al., Replacing Judges with Juries ↗

Bias 4 · Calibration and score drift

Scores wander unless you anchor them

Ask a judge for “a score from 1 to 5” and it decides for itself what a 3 means, differently from run to run. Scores also drift when the model, the prompt or the rubric changes.

  • Cut randomness: use temperature 0 where your model allows it. Some newer models don’t, so run the judge a few times and take the majority.
  • Anchor the scale: describe each point with a concrete behavior, like the example here. Many teams go further and use pass/fail per criterion.
  • Stop the drift: pin the model version, version the rubric, and rescore a fixed anchor set after every change.

Sources: Shankar et al., Who Validates the Validators? ↗ · Hamel Husain, LLM judges that drive results ↗

Pairwise vs. pointwise

Compare two, or score one?

Pairwise asks “which is better, A or B?” Judges are more sensitive comparing than scoring, so it’s the better choice for picking between two prompts or models. To rank many, run head-to-head matches and turn the wins into Elo-style ratings, as Chatbot Arena does.

Pointwise asks “how good is this one?” against a rubric. It gives you an absolute score you can set a threshold on, so it’s what you use to gate releases and monitor production.

Source: Chiang et al., Chatbot Arena ↗

Meta-evaluation

Prove the judge before you deploy it

Have experts label a set of real outputs, run the judge on the same set, and measure how well they agree. Raw agreement misleads: if 90% of outputs pass, a judge that always says “pass” agrees 90% of the time and catches nothing. Try it.

  • Cohen’s kappa for pass/fail labels: agreement after removing what chance alone would give. 1 is perfect, 0 is chance. Use weighted kappa for 1–5 scores.
  • Spearman correlation for scores: do the judge and the experts rank outputs in the same order?
  • The bar: aim for the agreement your experts reach with each other, and check how many real failures the judge catches.

Sources: Cohen (1960), A coefficient of agreement ↗ · Landis & Koch (1977) ↗ · Hamel Husain ↗

Before you ship a judge

A production checklist

  • One criterion per judge, with pass and fail written out
  • Pass/fail, or a scale where every point is anchored
  • Pairwise runs in both orders; flips count as ties
  • The rubric says length isn’t quality
  • A judge from a different model family than the generator
  • Model version pinned and rubric versioned
  • Kappa or Spearman measured against expert labels
  • A fixed anchor set rescored after every change
