Deconstructing RAG

Decoupling retrieval performance from synthesis quality

What is RAG?

RAG stands for retrieval-augmented generation. It’s how an AI assistant answers from your own documents instead of only from what it learned in training. When a question comes in, it first searches your documents for the most relevant passages, then hands them to a large language model (LLM), which writes the answer from them. Help-center bots and company-wiki assistants usually work this way.

So a RAG system has two jobs: find the right passages, then write an answer from them. When an answer is wrong, you need to know which job failed. Grade the retrieved passages and the written answer separately, and you fix the half that broke instead of guessing.

Decouple the two halves

Which half failed?

One end-to-end score can’t tell you whether to fix the retriever or the prompt. Score them separately and every bad answer lands in one box, and each box has a different fix.

Retrieval metrics

Did we find the right chunks, near the top?

For each test question, mark which chunks are relevant, then score the ranked list the retriever returned. Tap a chunk to change its label, or move K.

  • Precision@K: of the top K chunks, how many are relevant?
  • Recall@K: of all the relevant chunks, how many made the top K?
  • MRR (mean reciprocal rank): 1 ÷ the position of the first relevant chunk, averaged over questions. Rewards putting a good chunk first.
  • NDCG@K (normalized discounted cumulative gain): adds up credit for every relevant chunk in the top K, counts each one less the lower it ranks, and divides by the best possible score, so 1.0 means the best order.

Sources: Manning et al., Introduction to Information Retrieval ↗ · Järvelin & Kekäläinen, Cumulated gain ↗

Generation metrics · the RAG triad

Three checks between question, context and answer

  • Faithfulness (groundedness): did the answer stay strictly within the retrieved context? Every claim should be supported by a chunk.
  • Answer relevance: did the answer directly address the question, rather than something near it?
  • Context relevance: was what we retrieved relevant and free of noise? Noise dilutes the prompt and invites wrong answers.

Each is usually scored by an LLM judge, so check those judges against human labels first.

Source: Es et al., RAGAS ↗

Faithfulness, up close

Check the answer claim by claim

Split the answer into individual claims and check each one against the retrieved chunks. The score is the share of claims the context supports. One unsupported claim is a hallucination, even when it happens to be true.

Synthetic test sets

Bootstrap a test suite from your own documents

Before you have real traffic, have an LLM read a chunk and write a question it answers, plus the answer. Each query-chunk-answer triplet becomes a test: retrieval should find that chunk, and generation should match that answer.

Then make it honest: filter out questions that copy the chunk’s wording, read a sample by hand, and replace synthetic questions with real ones as users arrive.

Source: Saad-Falcon et al., ARES ↗

CI/CD regression testing

Gate every retrieval change

CI/CD (continuous integration and continuous delivery) means every code change is tested automatically before it ships. Regression testing checks that nothing got worse. Chunk size, the embedding model and the re-ranker all change answers in ways nobody predicts, so run the eval suite on every change, compare against the current baseline, and block the merge when a gate fails.

Gate both halves, plus cost and latency, and keep a holdout set nobody tunes against.

Before you ship RAG

A checklist

  • Retrieval and generation are scored separately
  • Relevant chunks are labeled for every test question
  • Recall@K where you need coverage, MRR or NDCG where order matters
  • Faithfulness checked claim by claim
  • LLM judges checked against human labels
  • Synthetic questions filtered and replaced by real ones over time
  • Every chunking, embedding and re-ranking change runs the gates
  • A holdout set nobody tunes against

Terms you’ll see

The vocabulary, in plain English

RAG retrieval-augmented generation
Answering from your own documents: retrieve relevant passages first, then generate an answer from them.
LLM large language model
The AI model that writes the answer, like Claude.
Chunk
A short passage your documents are split into, so the system can fetch just the part that matters.
Retriever
The search step that finds the chunks most related to the question.
Embedding
A list of numbers that captures what a text means, so texts with similar meanings can be found by comparing numbers. Searching this way is called semantic search.
Re-ranker
A second model that reorders the retrieved chunks so the most useful ones come first.
Top K, or @K
The first K chunks the retriever returns. A metric “@K” only looks at those, for example @5 means the top 5.
Precision@K
The share of the top K chunks that are relevant.
Recall@K
The share of all the relevant chunks that made it into the top K.
MRR mean reciprocal rank
For each question, 1 divided by the position of the first relevant chunk (1 if it’s first, ½ if second, ⅓ if third), averaged over all questions.
NDCG normalized discounted cumulative gain
Scores the whole ranking. Each relevant chunk earns credit (cumulative gain), less the lower it sits (discounted), divided by the best possible score (normalized), so 1.0 is a perfect order.
Faithfulness also called groundedness
The answer only says what the retrieved chunks support.
Hallucination
A claim the model made up that the sources don’t support.
LLM judge
A model that grades another model’s output against a written rubric.
Synthetic test set
Test questions an LLM writes from your documents, used before you have real user questions.
CI/CD continuous integration and continuous delivery
Testing and shipping every code change automatically. A quality gate stops a change whose tests fail.
Regression
Something that used to work gets worse after a change.
Baseline
The current version’s scores, which a change is compared against.
p95 latency 95th percentile
The response time 95% of requests beat; the slowest 5% take longer.
Holdout set
Test questions nobody tunes against, so the scores stay honest.
