Evals

How to tell whether an AI product actually works, on one page. AI gives different answers to the same question, so you can’t test it once and trust it. An eval is a repeatable test you run on many examples, many times, every time something changes.

The eval loop

Key terms

Eval
A repeatable test of whether an AI product does what it should, scored over many examples rather than one.
Golden set
Examples where you already know the right answer. Mix easy, tricky and adversarial ones; 20 good examples beat 500 random ones.
Grader
Whatever decides pass or fail for one output: a code check, an LLM judge, or a person.
Code check
A plain program that tests something objective, like length, format, banned words or links. Fast, free and the same every time.
LLM as judge
A model answers a yes/no question about an output, for things code can’t check, like “Is this reply specific?” (An LLM, or large language model, is the kind of AI Claude is.)
Rubric
The written definition of pass and fail for one judge, with an example of each.
Calibration
Checking a judge against people before trusting it: label about 20 outputs yourself and count how often the judge agrees.
Trace
The step-by-step record of what an agent did: every tool call, every result, every decision.
Error analysis
Reading the failures and grouping them by cause, so you fix the biggest problem first.
Pass rate
The share of cases that pass. Run each case a few times and also count how often it passes every time, because answers vary.
Regression
Something that used to work breaks after a change. A saved eval set catches it before your users do.
Offline and online evals
Offline: saved examples, before launch, as often as you like. Online: real users after launch, through product metrics and A/B tests.
A/B test
Show the old and new version to similar groups and compare a real outcome, like click-through or task success.
Fakes
Pretend versions of tools and services, so a test can’t send, buy or post anything real.
Planted bug
A mistake you add on purpose to prove your eval would catch it. If the eval still passes, the eval is broken. Also called mutation testing.
Dry run
Do everything except the real action, and show what would have happened.

Writing a good LLM judge

  • Ask one question per judge. Five rules means five judges.
  • Ask yes or no, not 1 to 5. Scores drift; yes/no stays steady.
  • Write down what pass and fail mean, with an example of each.
  • Calibrate before you trust it: if you and the judge disagree, fix the judge’s question first.
  • Recheck it whenever you change the judge’s prompt or model.

Common mistakes

  • Testing once. Answers vary, so run each case several times.
  • Averaging away failures. One bad answer can matter more than a good average.
  • Only easy examples. Add the tricky and adversarial ones on purpose.
  • Trusting a judge nobody checked against people.
  • Changing several things at once, so you can’t tell what helped.
  • Measuring what’s easy instead of what matters to users.
