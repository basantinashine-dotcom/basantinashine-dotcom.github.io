Guardrails & Safety for Autonomous Agents

Three layers of defense, and when to ask a human

What are guardrails?

Guardrails are the checks around an AI agent that stop it from causing harm: following instructions it shouldn’t, taking actions it shouldn’t, or saying things it shouldn’t. A prompt asks the model to behave. A guardrail is code that makes sure, whatever the model decides.

An autonomous agent reads text from strangers, calls real tools and changes real systems. No single check catches everything, so put one at each layer: what comes in, what the agent does, and what goes out.

Three-layer defense

Check what comes in, what it does, what goes out

Each layer catches what the others miss. An injection that slips past the input checks still can’t move money past the execution limits, and a made-up number still gets caught before the customer sees it.

Source: OWASP Top 10 for LLM Applications ↗

Layer 1 · Input

Treat everything it reads as data, not orders

  • Direct prompt injection: a user types “ignore your instructions and…”. Detect it with a classifier and refuse.
  • Indirect prompt injection: the instructions hide in something the agent fetches, like a web page, an email, a document or a tool result. Mark fetched text as untrusted, and never let it grant permissions or trigger actions on its own.
  • Jailbreak filters: catch role-play and other tricks meant to talk the model out of its rules.
  • PII masking: replace personal data, like names, card numbers and addresses, with placeholders before it reaches the model or the logs.

Sources: Greshake et al., Indirect Prompt Injection ↗ · Simon Willison, Prompt injection ↗ · Microsoft Presidio ↗

Layer 2 · Execution

Limit what the agent can actually do

  • Tool boundaries: give each task only the tools it needs, with credentials scoped to match.
  • Dry-run previews: show exactly what will change before it changes.
  • Deterministic parameter validation: code checks every argument against rules, like “the refund can’t exceed the order total.”
  • Rate limits: cap actions per minute and per day, so a loop can’t run away.
  • Rollback hooks: every write has an undo, and every action lands in an audit trail.

Sources: OWASP, Excessive Agency ↗ · Anthropic, Building effective agents ↗

Layer 3 · Output

Check what it says before anyone sees it

  • Hallucination detection: every number, name and date in the reply must match the sources or tool results it came from.
  • Brand safety filters: tone, banned topics, legal or medical claims, competitor mentions.
  • Structured schema conformity: when another system reads the output, validate it against the expected format; if it fails, retry or fall back.
Human-in-the-loop thresholds

Decide when the agent must ask

Set the threshold by stakes and reversibility. Money over a limit, bulk changes, messages that leave the company and anything you can’t undo should pause for a person. Pick an action to see where it lands.

Make escalation graceful: the agent packages what it wants to do, why, and how to undo it; keeps working on everything else; and if nobody answers in time, does nothing rather than guessing.

Fail-soft UI patterns

When it can’t finish, say what happened

Agents fail partway through: a tool is down, an approval is pending, a check blocks a step. A blank error or a fake “Done!” breaks trust. Fail soft instead:

  • Show progress step by step: done, waiting, couldn’t do.
  • Say why in plain words, and what happens next.
  • Keep what was finished, and save the request.
  • Offer one clear next action, including reaching a person.

Source: Google PAIR, Errors and graceful failure ↗

Before you ship an agent

A checklist

  • Fetched content is marked untrusted and can’t trigger actions
  • Personal data is masked before the model and the logs
  • Each task gets only the tools and credentials it needs
  • Every tool argument is validated in code
  • Rate limits, an audit trail and an undo for every write
  • Money, bulk changes, outside messages and deletes pause for a person
  • Replies are checked for facts, tone and format before sending
  • Failures show progress, the reason and a next step
  • Injection and misuse attempts are part of the test suite
  • A kill switch can stop the agent at once

Terms you’ll see

The vocabulary, in plain English

Autonomous agent
An AI system that plans and takes actions with tools, step by step, toward a goal, without a person approving each step.
Guardrail
A check, usually in code, that stops an agent from following, doing or saying something it shouldn’t.
Prompt injection
Text written to make the model ignore its instructions. Direct: typed by the user. Indirect: hidden in something the agent reads, like a web page or email.
Jailbreak
A trick, like role-play, meant to talk the model out of its safety rules.
PII personally identifiable information
Data that identifies a person, like a name, address, phone number or card number.
Masking also called redaction
Replacing sensitive data with a placeholder, like [CARD], before the model or the logs see it.
Tool call
The agent asking your code to run a function, like issue_refund, with arguments it chose.
Least privilege
Giving each part only the access it needs for the task, and nothing more.
Dry run
Doing everything except the real change, and showing what would happen.
Parameter validation
Code checking every argument of a tool call against fixed rules before it runs.
Rate limit
A cap on how many actions can happen in a period, like 50 emails a day.
Rollback an undo
A way to reverse a change after it’s made.
Audit trail
A permanent record of every action: what, when, why and on whose behalf.
Hallucination
A claim the model made up that its sources don’t support.
Brand safety
Keeping outputs within your company’s tone and rules: no off-limits topics, claims or language.
Schema
The exact format another system expects, like a JSON object with specific fields.
HITL human-in-the-loop
A person reviews or approves before certain actions happen.
Escalation
Handing a decision to a person, with the context they need to make it.
Fail-soft
Failing in a way that keeps finished work, explains what happened and offers a next step. The opposite of a blank error.
Kill switch
A way to stop the agent immediately, everywhere.
